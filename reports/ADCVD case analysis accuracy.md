# Rebuild AD/CVD analysis around official sources

HTS Hero can reach best-in-class AD/CVD accuracy. Getting there means more than better regexes or more AI. The pipeline has to stop inferring from Federal Register notice titles alone. It should rebuild every fact from official sources, each used for the field it is authoritative on. The **USITC IDS daily JSON** tells us whether a case exists and its order, continuation and revocation dates. **Federal Register and GovInfo text** gives the legal events with their effective dates. **ITA case pages** give current scope text and rulings. **CBP public AD/CVD messages** give order-time codes and current cash deposits by exporter. A **monthly ITA dashboard export** is the reference to check against. The current system rebuilds everything from FR text with title regexes, and its main problem is precision, not recall. On its own 98 checks it finds every expected case (89 correct, 0 missed). But for China, 2,722 of 21,528 HTS lines flag at least one case, adding up to 6,873 case flags. Many of these are "likely" flags from broad scope codes or "possible" flags from a 6-digit fallback. Prod shows the same failure on status: it lists revoked orders as live, suspension agreements as orders, and petitions as "unknown". It does this because its status comes from hand-run dev scripts that prod never ran. The fix is architectural. Keep raw documents immutable. Derive versioned extractions and dated events from them. Compute status as a pure function over those events, and have prod rebuild itself whenever the code changes, so dev never copies data to prod. Matching becomes a two-stage process: deterministic codes and country produce candidates, then a scope- and exclusion-aware layer decides "likely" and quotes its evidence. Each step ships only after it beats a measured baseline. The phantom cleanup and status fixes that were put on hold become the first two consumers of this design: a registry gate that fails closed, and a status fold that prod recomputes itself. They are not one-off data patches. AI cost stays small, at a few dollars a month in steady state and about $10 for a full Haiku re-pass of the corpus.

## The current pipeline finds the cases but over-flags them

Every AD/CVD fact in HTS Hero today comes from Federal Register text read with regex. The inputs are about 12 months of ITA/ITC notices, each case's FR docket titles back to 1994, ITA case pages and CBP's public message feed. Status comes from a hand-written state machine over notice titles, patched with two date rules: an "investigation" older than 730 days becomes "terminated", and an undated "order" initiated within 548 days becomes "investigation" (`libs/adcvd/notices.ts`, `libs/adcvd/checks.ts`). Matching uses only two inputs, HTS code and country. "Likely" means a current main code (or a same-8-digit replacement of one) for the case's own country on a live case. Anything else touching the code is "possible" (`libs/adcvd/match.ts`). The matcher never sees the product description, the manufacturer or exporter, entry dates, scope rulings or written exclusions.

Measured on its own terms the core works. The golden run on 2026-10-26 scored **89 correct, 0 missed, 3 false "likely" and 6 "possible" noise across 52 imports and 98 checks**. Those numbers are in-sample, though. The set was written while the fixes were being built. Half of it is China. It also ignores 33 extra flags the matcher emitted on cases the set doesn't mention (`scripts/adcvd/golden.ts`, golden output in the audit scratchpad). The whole-HTS sweep measures what users actually see. Running the real matcher over all 969 dev cases and every current HTS line flags 2,722 Chinese lines (1,393 with a "likely") with 6,873 case flags. The fallback that flags any line sharing 6 digits with a main code (`same_subheading`) alone produces 2,151 "possible" flags for China. Single lines such as 7326.90.8688 and 9403.20.0011 flag 13 cases at once. Specific defects turn a correct code match into a wrong product match:

- **Aluminum extrusions (A-570-967/C-570-968):** the scope really does name 9403.20.00 (other metal furniture) as "currently classifiable". So every Chinese metal-furniture import gets a "likely" extrusions flag.
- **PET resin (A-570-024):** its main code covers the whole 3907.69 "Other" line, so low-viscosity PET outside the scope's viscosity floor flags "likely".
- **Short main codes:** 50 six-digit and 346 eight-digit main codes make every child line "likely".

This matters beyond user annoyance. Commerce's own guidance says the narrative scope is "dispositive" because only part of an HTS subheading may be covered ([ITA Scope Ruling Guidance](https://access.trade.gov/help/Scope_Ruling_Guidance_(4.1.2022).pdf)). Commercial incumbents present AD/CVD as one more field on the tariff line and publish no method or accuracy figure ([ONESOURCE GTC brochure](https://store.tax.thomsonreuters.com.au/content/dam/ewp-m/documents/tax/en/pdf/brochures/onesource-global-trade-content-brochure.pdf)). The clearest public description of a better design comes from a small entrant, Tandom. It says plainly that "the HTS code alone does not decide whether an order applies", and it cites a source for every match ([Tandom](https://compliance.tandom.ai/)). No vendor, broker or agency publishes AD/CVD screening precision or recall. A measured, published accuracy figure would therefore set HTS Hero apart, not just bring it level. A noisy "likely" also does real harm. Enforcement now reaches hundreds of millions of dollars: a $549.5M FCA resolution over aluminum extrusions declared as pallets, and $4.9M over "sham" furniture kits ([AFS Law](https://www.afslaw.com/perspectives/investigations-blog/baseline-not-finish-line-fca-customs-enforcement-mid-year-2026)). A screen whose flags users learn to ignore fails exactly where the risk is highest.

The second failure is operational, and prod shows it now. Prod's hourly cron timed out at 300 s every hour until PR #297 deployed on 2026-10-26. ITA runs last in each cron run, so ITA scope codes were never fetched in prod. On 2026-10-26, prod's public `/api/adcvd/index` differed from dev on the codes of 349 live cases. For example, prod still matches A-570-137 (R-125) only on the never-existed 2903.49.1010. About 17 statuses also differed:

- Revoked orders A-580-903, A-570-093, C-570-094 and A-560-836 show as live orders.
- The fence-picket petitions and A-570-225 show as "unknown".
- The sugar and Ukraine plate suspension agreements show as orders.
- Phantom numbers such as C-583-840 are still live.

None of this is a matter of the data being in the wrong database. Dev corrected these statuses with hand-run scripts (`recompute`, `phantoms`), and prod's code never re-derives (`package.json`, `scripts/adcvd/*`). Dev also still has two live, matchable phantoms (A-570-957, A-533-849), because the phantom script deletes a case only when its FR docket is empty, and FR docket tags are themselves mis-tagged (`scripts/adcvd/phantoms.ts`). The phantom check that runs on new numbers also trusts any new number whenever the FR API is blocked (`libs/adcvd/notices.ts`). So the very outage that blocks the check is when phantoms get created.

## Each field has one authoritative source, and none covers everything

The source research changes the design more than anything else here. Different agencies own different facts, and the current pipeline asks the Federal Register to answer all of them. The table below assigns each field a primary source, a second source, and the disagreements actually observed.

| Field | Primary source | Second source / check | Observed disagreement |
|---|---|---|---|
| Case exists; AD vs CVD; country | USITC IDS `Commerce Orders` + votes ([IDS JSON](https://ids.usitc.gov/investigations.json)) | ITA case-page header; FR `docket_ids`; CBP case messages | Palladium RU: ITA page exists but is empty; ITC final was negative and no order issued |
| Status | FR events with effective dates, folded | IDS order/continued/revoke dates; CBP REVORD; ITA dashboard export (reference) | IDS misses 65 revocations ITA lists; ITA case page has no status field |
| Scope text | ITA case page "Scope of the Order" ([A-570-979](https://beta.trade.gov/adcvd?adcvdcase=A-570-979)) | FR order notice | HFC blends: notices keep 3824.78, ITA scope has 3827.6x |
| Scope HTS codes | ITA scope text + CBP order message, checked against current HTS | ITA HTS list (hint only) | R-125: ITA list keeps non-existent 2903.49.10.10, CBP order message does not ([CBP msg 2066405](https://trade.cbp.dhs.gov/ace/adcvd/service-messages/messages/public/getMsgBody/2066405)) |
| Renumbered codes | USITC revision exports + Census impconcord02–26 | HS correlation tables; ITA "HTS Change(s)" column | Kegs: every source cites dead 7310.10.0010/.0050; current is 7310.10.0005 ([HTS search](https://hts.usitc.gov/reststop/search?keyword=7310.10.00)) |
| Cash deposit by exporter | CBP CD messages (sub-case numbers, deactivations) | FR final results | FR lacks sub-case numbers like A-570-137-011 |
| Rulings, circumvention, deadlines | ITA case-page rulings table and "Upcoming Announcements" | ACCESS documents; CBP SCOINQ messages | Only ITA pages carry upcoming deadlines |

**IDS is the best machine-readable source for whether a case exists.** It is a 37 MB public export, refreshed daily: 4,434 investigations, and 2,654 Commerce order rows covering 1,140 distinct case numbers. Each row has the order issuance date, the continuation date, and the revocation or termination date ([USITC IDS JSON](https://ids.usitc.gov/investigations.json)). It also records the negative ITC final vote that stopped palladium from Russia, a case for which Commerce published no termination notice at all ([FR 2026-12219](https://www.federalregister.gov/d/2026-12219)). Its flaws are concrete:

- It is missing revoke dates for 65 cases that ITA lists as revoked.
- 51 in-effect cases appear with malformed numbers ("A–557–827", "A-552- 836", "[A-533-924").
- One field holds both order dates and suspension-agreement dates, so the two can't be told apart.
- It records revocations by FR publication date, not effective date.
- It shows a German kegs revocation dated a year before that order was issued.

So IDS seeds and corroborates the registry. It never overrides a revocation on its own.

**The ITA ADCVD Proceedings dashboard is the only official list that states status for every case.** Its 2026-10-23 export held 858 in-effect rows (851 orders and 7 suspension agreements), 422 revoked rows and 88 investigations. It reflected a new order within 15 days of publication ([ITA dashboard](https://www.trade.gov/data-visualization/adcvd-proceedings)). It is a Power BI embed with no API or feed. Export is manual, so it serves as a monthly reconciliation reference, not an input to the pipeline. ITA's case pages on beta.trade.gov are server-rendered HTML that plain fetches can read (www.trade.gov now returns 404). They carry current consolidated scope text, the rulings table with ACCESS links, and upcoming review deadlines. They carry no status, dates, rates or companies. Their HTS lists can be stale (kegs, R-125), empty (sugar, whose scope names 18 codes), or broader than the scope (solar lists four extra 8541.40.60 suffixes) ([A-570-137](https://beta.trade.gov/adcvd?adcvdcase=A-570-137); [C-201-846](https://beta.trade.gov/adcvd?adcvdcase=C-201-846)). One property makes them very valuable. **Every URL returns 200, but a non-existent number renders an empty "Case #" header.** That makes the page a cheap check for whether a case exists, and it caught all five phantoms tested ([C-821-824](https://beta.trade.gov/adcvd?adcvdcase=C-821-824)). The pipeline must read the header, not the HTTP status, and it must check that the page's country and product match. Several typos land on real but unrelated old numbers: A-583-839 is a 2002 Taiwan cold-rolled case, and A-821-824 is Russian wire rod.

**CBP's public message service is open JSON with no login.** A per-case search (`quickSearchMessage-ServerSide/<case>`) returned all 14 R-125 messages from initiation in 2021 to automatic liquidation in 2026. Message bodies give exporter-level cash deposits with sub-case numbers. For R-125, Sanmei's sub-case is 48.67% and the China-wide rate is 267.51%, and the China-wide figure agrees with the FR final results ([CBP msg 6083439](https://trade.cbp.dhs.gov/ace/adcvd/service-messages/messages/public/getMsgBody/6083439); [GovInfo 2026-05002](https://www.govinfo.gov/content/pkg/FR-2026-03-16/html/2026-05002.htm)). A REVORD message corroborates a revocation, 5 to 37 days after the FR notice in the cases checked ([CBP A580903](https://trade.cbp.dhs.gov/ace/adcvd/service-messages/messages/public/quickSearchMessage-MemorySide/A580903)). The current pipeline reads only `getLatestMessages`, which holds a few days of messages, so cron downtime loses data permanently (`libs/adcvd/cbp.ts`). The per-case history endpoint removes that gap. The ACE case reference file itself, with authoritative statuses, HTS lists and rates, needs an ACE login and stays out of reach ([CBP guidance](https://www.cbp.gov/document/guidance/adcvd-cases-and-messages)).

**The FR stays the legal source of record, but HTS Hero should use the FR API only for metadata and search.** Scripted HTML and documentation requests now redirect to a CAPTCHA page, and parallel API calls got this machine's IP blocked ([unblock.federalregister.gov](https://unblock.federalregister.gov/)). GovInfo serves the same text at `content/pkg/FR-<date>/html/<doc>.htm` with no key, and as daily bulk XML that can be filtered locally by agency ([GovInfo bulk FR 2026/10](https://www.govinfo.gov/bulkdata/json/FR/2026/10)). For code lineage, Census `impconcord23` to `impconcord26` all download, though the index page lists files only through 2022 ([impconcord23.xlsx](https://www.census.gov/foreign-trade/reference/codes/concordance/impconcord23.xlsx)). That closes the missing 2023 and 2024 snapshots in `tariffs/hts-concordance/successors.json`. Secondary datasets are no shortcut. Global Trade Alert is CC BY-NC ([GTA terms](https://globaltradealert.org/terms)), WTO I-TIP stops in mid-2020, and the old ITA AD/CVD API fails TLS with an expired certificate. ITA's terms also bar using the API key embedded in its search bundle ([ITA ToS](https://developer.trade.gov/terms-of-service)).

## Status has to be folded from dated events, not read from titles

**Status errors follow a short list of known traps, and every status error found in prod fits one of them.** The ground-truth check covered 21 case numbers: 3 live orders, 3 live suspension agreements, 4 revoked, 3 terminated by ITC negatives, 1 in investigation, 2 petitions only, and 5 that never existed. A title-only parser gets nearly every hard one wrong, for one of six reasons:

1. **ITC negative finals hide the negative in the body.** The title says only "Determinations". The text says "not materially injured", or, for active anode material, "not materially retarded", a phrase a regex for "injured" misses ([FR 2026-06488](https://www.federalregister.gov/d/2026-06488)).
2. **An affirmative Commerce final creates no order.** Palladium and active anode material both had one and then lost at the ITC ([FR 2026-08487](https://www.federalregister.gov/d/2026-08487)).
3. **"Termination of the Suspension Agreement and Issuance of Antidumping Duty Order" means the case becomes an order**, not that it ends. Russian CTL plate (A-821-808) is an example ([FR 2023-17407](https://www.federalregister.gov/d/2023-17407)).
4. **Suspension-agreement reviews look like order reviews.** The sugar and Ukraine plate cases get labelled orders this way ([FR 2025-18222](https://www.federalregister.gov/d/2025-18222)).
5. **Omnibus lists keep naming revoked orders for stub periods.** Examples are kegs "12/1/24–12/15/24", PET sheet "9/1/25–9/9/25", and mattresses with a "revoked due to litigation" footnote. **Court "Amended … Order" notices can also land after a revocation.** Both revive dead orders in a naive parser ([FR 2026-13892](https://www.federalregister.gov/d/2026-13892); [FR 2024-28946](https://www.federalregister.gov/d/2024-28946)).
6. **Effective dates come before publication.** PET sheet Korea was revoked effective 2025-09-10 but published 2026-01-12, so an FR-only list shows it live for four months ([FR 2026-00384](https://www.federalregister.gov/d/2026-00384)).

The prod differences listed earlier are traps 3 to 6 plus petitions that were never initiated: A-570-243/C-570-244 are still at the stage where Commerce extended its deadline to decide on initiating ([FR 2026-21285](https://www.federalregister.gov/d/2026-21285)).

The fix is to model status as a pure function. Store events, not a status column. Each event needs a type, publication date, effective date, the source document, a supporting quote, the companies it affects, and whether it supersedes the previous deposit rate. Status is then a fold over events ordered by effective date, then publication date, through a transition table that is unit-tested and that rejects impossible sequences. A rejected sequence (an order before an ITC affirmative, a list row "continuing" a revoked case) means an event was missed. It goes to the /admin "Needs You" queue; it is never patched silently. The transition table should encode the following rules:

- A list row, a court-amended order, or a CBP liquidation or cash-deposit message never revives a revoked order.
- "Agreement Suspending" titles keep the case suspended.
- Termination of a suspension agreement with an order issued moves the case to order.
- An ITC "Determinations" body with either negative phrase, scoped to the countries it names, terminates the investigation.
- A petition is its own state, and it is not matchable as an investigation.
- "Unknown" is never matchable.

The 548/730-day heuristics then go away. Today they patch over missing events and still leave 20 "investigations" more than 365 days old, among them float glass from Malaysia, initiated 2025-01-08 (`libs/adcvd/checks.ts`).

Corroboration and reconciliation sit on top of the fold. IDS supplies continuation dates the docket query misses. 59 of 851 dated orders currently have a "last continued" date more than 5.5 years old, so their sunset estimates are already in the past (A-489-826 is one). IDS also supplies revocation dates as a second witness. A CBP REVORD message confirms a revocation. Because sunset revocations fall on a predictable anniversary, an order whose sunset review was initiated and that has no continuation by the deadline can show as "possibly revoked" before the FR notice arrives. The ITA dashboard export is reconciled monthly. On revoked-versus-live, ITA wins over IDS: ITA had no live-but-revoked errors in the comparison, while IDS lacked 65 revocations ([ITA dashboard](https://www.trade.gov/data-visualization/adcvd-proceedings); [IDS](https://ids.usitc.gov/investigations.json)). Every disagreement becomes an admin item, not an automatic overwrite, so the pipeline stays auditable and the dashboard keeps its value as an independent check.

The registry needs the same discipline. Typos follow three patterns: wrong letter (C-555-003, A-533-849, C-821-824), wrong country code (583 for Türkiye's 489), and a wrong serial digit (A-557-857 for A-557-827). The fix is to require corroboration before a number becomes a case. A number seen only in an omnibus list must pass four checks:

- its letter matches the list section;
- its country code matches the country heading;
- the ITA page header shows the same country;
- the page's product fuzzy-matches the row's product.

When a check fails, the gate looks for the nearest real case in the registry (a letter flip, a one-digit edit, or a swapped country code) and maps the row to it. Otherwise the number is quarantined. It is kept for audit, never matched, and never deleted. If the oracle can't be reached, the gate quarantines (fails closed). Before any join, case numbers are normalized: en and em dashes become "-", and spaces and brackets are stripped.

## Codes nominate candidates; scope text decides "likely"

**Experts work through scope in a set order, and the matcher should follow the same order.** First, HTS code and origin nominate candidate orders. Next comes the scope's inclusions, exclusions, and kit or finished-goods carve-outs. Then prior scope rulings. Then the producer and exporter, which set the rate through the combination → exporter → all-others / country-wide waterfall. Finally, the importer documents the rationale when disclaiming an order ([C.H. Robinson checklist](https://www.chrobinson.com/en-us/resources/resource-center/guides/customs-clearance-checklist/); [Tandom guide](https://tandom.ai/resources/how-to-check-adcvd-exposure-by-hts-code)). The carve-outs are fact-specific enough that courts keep remanding them. For aluminum extrusions, a "finished goods kit" must contain at importation every part needed to assemble the final good, and fasteners alone don't qualify ([CIT Slip Op. 23-05](https://www.cit.uscourts.gov/sites/cit/files/23-05.pdf)). That is why HTS code plus country can only nominate.

**Scope codes become labelled facts with a source, not a merged list.** Each code from each source (ITA scope text, FR order, CBP order message, ITA HTS list, ITA rulings "HTS Change(s)") is stored with its role (in-scope main, "may also enter", excluded, convenience-only), a verbatim quote, the source document, and its status in the current HTS. Regex should extract the codes, because they appear in highly regular sentences. An LLM labels the roles under a strict JSON schema, with a `quote` field per code. Code then checks deterministically that the quote appears in the cached raw text, and stores its character offsets. A workaround is needed here because Claude's Citations feature returns a 400 error when combined with structured outputs ([Claude docs: Citations](https://platform.claude.com/docs/en/build-with-claude/citations)). Every regex code must receive an LLM role, and every LLM code must exist in the regex set. Disagreement, a failed quote, or a status-changing notice escalates from Haiku to Sonnet. Voting runs only on those escalated fields, because self-consistency gains are real but small on easy fields ([AIMS ACI 2026](https://www.aimspress.com/article/doi/10.3934/aci.2026010)). This replaces the current paragraph-level rule, under which any coded sentence in a paragraph that mentions an exclusion counts as excluded. That rule once excluded R-32's own code (`libs/adcvd/parse.ts`). Two other defects go with it: the Sonnet check reads the 12,000-character capped scope instead of the full text, and the same cases are re-checked up to 25 times. Together those repeats spent $2.80 of the $7.35 Sonnet scope bill.

**Mapping to the current HTS becomes a lineage graph, not a flat successors map.** Its nodes are (code, first revision, last revision). Its edges come from diffing consecutive USITC revision exports and are typed renumber, split, merge or reshuffle. Census concordances and description similarity serve as evidence for each edge. Pierce and Schott's "families" method shows why this matters: 7,503 of the 16,836 import codes active in 2004 had been revised since 1989 ([Pierce & Schott, FEDS 2012-16](https://www.federalreserve.gov/econres/feds/concording-us-harmonized-system-categories-over-time.htm)). A 1:1 renumber keeps the code's role. Split descendants become "possible" until scope text or a CBP message names them. Never-existed codes (R-125's 2903.49.1010; A-428-820's "7304.3900.16", which the current regex turns into the junk code `390016`) are handled separately. Candidates are generated only from valid codes within edit distance 1 or 2 under the same 6- or 8-digit prefix. They are ranked by description match, with an LLM tie-break limited to those candidates. The code is shown as "order cites X, which does not exist; likely intended Y". Constraining the candidates matters because unconstrained models invent codes; HSGraphAgent constrains them to a code graph for this reason ([HSGraphAgent, ACL 2026](https://preview.aclanthology.org/ingest-acl/2026.acl-long.2072/)). R-125 shows why CBP's order message is worth reading as a source. It lists 2903.49.0000 rather than the typo that the FR order and ITA list both carry.

**"Likely" then needs three things beyond code and country.** The first is specificity. A main code at 4 or 6 digits, a basket "Other" line, or a code in a scope that spans many chapters (the aluminum-extrusions pattern) yields "possible" unless the product layer supports it. The second is exclusion awareness. One cached AI call per (HTS-10, country, case, scope hash, description hash) reads the import's description, the user's product name, and the candidate's full scope text. A deterministic candidate set leaves only a handful of cases per import, so no retrieval is needed. The call returns in-scope, excluded or unclear, with a quoted controlling sentence. A verified exclusion quote drops the flag. A contradicting product description demotes it to "possible". The model's stated confidence is never used: verbal confidence is overconfident and only weakly tied to correctness ([arXiv 2603.22161](https://arxiv.org/pdf/2603.22161)). Confidence comes instead from observable signals, tuned on labelled data. The third is the company. Collect manufacturer and exporter, resolve the rate waterfall, and show the range across the rates that could apply when the parties are unknown. Description-only matching never produces "likely" by itself. The team's earlier test found it too noisy (14% false flags at 80% recall). Even fine-tuned models get only 40% of 10-digit HTS codes right on CROSS-ruling benchmarks ([ATLAS, NeurIPS 2025](https://neurips.cc/virtual/2025/129845)). The `same_subheading` fallback moves to a hidden "near" level. It returns only if the broker sheet's 40 near-miss rows show it recovers in-scope goods.

**Rates follow the same split between authoritative sources.** CBP CD messages, replayed in date order per sub-case with deactivations applied, give the current deposit rate per exporter. A table parser for the standard FR "Exporter/Producer | Weighted-average dumping margin (percent)" layout gives the legal rates. Haiku becomes a fallback, held to the same quote check. This removes the current rule that "the newest notice replaces the case's rates". A review covers only the companies reviewed, so that rule erases everyone else; it is the reason `all_others` is null on 211 of 843 rated orders. Court-ordered (Timken) notices change the deposit rate only when no later review has superseded it ([FR 2026-17770](https://public-inspection.federalregister.gov/2026-17770.pdf)), so they are events with a "supersedes" flag. Rates are always shown as % ranges and never added to the duty estimate. Third-country and circumvention findings come from the ITA rulings table, as structured events with their certification regimes. The solar circumvention orders, for example, let importers avoid deposits only with certifications signed by the time the entry summary was filed ([Foley](https://www.foley.com/insights/publications/2022/12/circumvention-solar-energy-products-se-asia/)). They replace the title regex that today finds third countries for only 9 cases.

## Target architecture and prioritized build plan

The target is a layered, event-sourced pipeline that production runs entirely by itself ([Databricks: medallion architecture](https://www.databricks.com/glossary/medallion-architecture)):

- **Raw:** immutable, content-addressed documents (FR metadata, GovInfo text, ITA pages, CBP message bodies, the IDS snapshot, HTS releases, Census files), each with a sha256 and fetch metadata.
- **Extractions:** keyed by (document hash, extractor version, model, prompt hash), stored permanently, because Batch API results expire after 29 days ([Claude docs: Batch](https://platform.claude.com/docs/en/build-with-claude/batch-processing)).
- **Events:** derived from the extractions.
- **Derived tables:** registry, status, current codes with roles, rates, and match candidates, rebuilt from events and the lineage graph.

Bumping an extractor version makes prod reprocess only the rows missing for the new key. That replaces `copy-to-prod` permanently and makes a dev/prod comparison a SQL diff at the same raw snapshot. Cost controls fall out of the same keys: identical inputs never call the model twice. ITA, backfill and re-derivation work each get their own budget line, so a large re-sort can no longer silently pause the current month's notice summaries, as the shared $20 budget can today (`libs/adcvd/process.ts`).

| Component | Decision | Why |
|---|---|---|
| GovInfo-first text, deadline-aware FR queue, 1-hour block memory (PR #297) | **Keep** | Fixed the prod 504s; matches FR's anti-scraping policy |
| ITA case-page reader (beta.trade.gov) | **Keep, extend** | Best scope and rulings source; add header-based existence check and the rulings table |
| Successors map, `mergeCodes` provenance | **Keep as input, replace with lineage graph** | Missing 2023/2024; needs typed edges and never-existed handling |
| Regex code extraction | **Keep** | Codes are regular; the LLM labels roles only |
| Title-regex state machine, 548/730-day heuristics, `recompute`/`phantoms` scripts | **Replace** | Event fold with effective dates, transition table, IDS/CBP corroboration |
| Paragraph-level exclusion rule; Sonnet re-sorts on capped text | **Replace** | Per-code role + verified quote, memoized by text hash |
| "Newest notice replaces rates" | **Replace** | Per-company merge; CBP CD replay; FR table parser |
| `copy-to-prod` | **Retire** | Prod re-derives from its own raw store |
| IDS daily ingest; CBP per-case history; monthly ITA reconciliation | **Add** | Existence, dates and status reference |
| Scope/exclusion AI layer; company waterfall; specificity rules | **Add** | Precision of "likely" |

The order follows the risk to users. Measurement comes first, so every later step is judged against a baseline.

## Evaluation that proves accuracy before anything ships

Nobody in the market publishes AD/CVD accuracy ([Tandom](https://compliance.tandom.ai/); [ONESOURCE](https://tax.thomsonreuters.com/en/products/onesource-global-trade-content.html)). HTS Hero's evaluation therefore has to set its own standard, and it should be built to be published. It has four truth sets, each measuring one layer.

**Status truth** is the ITA dashboard export (858 in effect, 422 revoked, 88 investigations on 2026-10-23), re-exported monthly. The 21-case lifecycle fixture is a permanent regression test, because it holds every known trap: ITC negatives with both phrases, suspension agreements, agreement-to-order, stub-period and court revivals, retroactive effective dates, petitions, and the five phantoms plus their real-number collisions. The metric is exact status match and correct effective date. Each residual must be explained by a cited document.

**Scope-code truth** is a new golden v2 of 150–300 cases, stratified by product family, country, era (before and after HS 2022) and event type, and seeded with every known renumbered or never-existed code. For each case it labels the codes in each role with quotes, plus the lineage-mapped current codes. Two people label it, a broker or the founder plus an Opus 5.5 pass, and the founder adjudicates disagreements and logs them. Even expert HS labels drift from the General Rules often enough to need an audit trail ([arXiv 2605.14857](https://arxiv.org/pdf/2605.14857)). The metric is set-level precision and recall per role.

**Match truth** combines the 220-row broker sheet, whose answer columns are blank today (`adcvd-review/review-2026-10-23.csv`), with a new out-of-sample import set that is no more than a quarter China. Scope rulings, EAPA determinations and FCA fact patterns supply labelled hard cases: kits, pallets, quartz described as marble, transshipment ([CBP EAPA 7552](https://www.cbp.gov/trade/trade-enforcement/tftea/eapa/recent-eapa-actions/eapa-action-determination-evasion-eapa-case-7552-quartz-surface-products)). The metrics are "likely" precision, with a target of at least 95% (an inferred target for alert-grade flags, not an industry figure), recall on in-scope goods, and the share of "possible" flags graded as noise. **Rate truth** compares sampled exporter rates with CBP CD messages, matching on sub-case.

These sets gate every change, the same way the HTS rate parser is already gated. Any parser, prompt, model or schema change runs the full suite plus the whole-HTS sweep, and it is blocked if any metric drops beyond a set tolerance. Gating matters because extraction results are sensitive to prompt, model and schema, and a more detailed prompt has been measured to do worse (59.3% vs 44.4%) ([medRxiv preprint](https://www.medrxiv.org/content/10.64898/2025.12.22.25342875v1); [arXiv 2606.05970](https://arxiv.org/pdf/2606.05970)). The golden runner moves into CI. New extractors run in shadow mode in prod first: they write to shadow derived tables, and a sample of the diffs is reviewed before promotion. Daily drift monitors feed /admin:

- new quarantined numbers;
- matchable cases without corroboration;
- investigations more than 365 days old;
- orders whose sunset date is past;
- unsummarized events;
- sweep flag counts per country;
- IDS-versus-registry disagreements.

The cron's existing "stopped" email covers only liveness. These monitors cover data quality.

## Conclusion

The current pipeline's core problem is not weak parsing. It has been asking one source, Federal Register titles, questions that other agencies answer authoritatively, and patching the gaps with date rules and hand-run scripts that prod never ran. Once each field is assigned its owner, most of the hard cases resolve mechanically: IDS for existence and dates, ITA for scope and rulings, CBP for deposits and order-time codes, and the ITA dashboard as an outside check. The phantom typos, the revived revocations and the misread suspension agreements are all instances of a few traps that a tested fold can handle. With that in place, prod's divergence from dev disappears, because prod rebuilds its own data on every deploy.

The bigger product opportunity is in the precision layer. Code-plus-country matching cannot tell metal furniture from aluminum extrusions, or low-viscosity PET from bottle-grade resin. A "likely" that quotes the controlling scope or exclusion sentence and states which producer and exporter rung applies is what separates an expert screen from a tariff-line field. Measuring that precision on an out-of-sample, broker-graded set is something no competitor has published. Two things remain unknown and should be treated as such. No one knows yet how well the exclusion-aware layer will score on real tracked imports. And the ITA dashboard's revocation lag hasn't been measured. Both questions are answered by the evaluation harness in step 0, which is why it comes first.
